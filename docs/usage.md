# Usage reference

[← Back to README](../README.md)

Detailed behavior and settings for Logline. For an interactive quick reference, open **More actions → Help** in the Logs panel.

## Capture and live tail

The first time the Logs panel opens after Logline is installed, it offers **Take the 1-minute tour** or **Explore on my own**, with quick starts for capturing a terminal, importing logs, adding a connection, and receiving OpenTelemetry. It shows once, and never after an update. The tour has seven stops (sources, connections, search, the table, the tabs, sharing, and the status bar); each dims the panel around one control and explains it, with **Back**, **Next**, and **Skip tour** (or Escape). Take it again from **More actions → Take the tour**, **Logline: Take the Tour**, or the guide's Get started section. VS Code's Welcome page also has a **Get started with Logline** walkthrough whose steps tick off as you capture, search, share, add a connection, and take the tour.

Open **More actions → Help** in the Logs panel for the offline **Logline Guide**. **Get started** walks through capturing a run, searching it, and sharing it with an agent, and ticks each step off once you have done it. Below it, cards for each area (capture, connections, search, inspection and analysis, traces and AI calls, comparing with production, sharing, and settings) say what a feature does and where it is; **Show me** points at the control in the Logs panel, opening its tab or menu first, and some cards run their command or open their setting. The search box in the guide's sidebar narrows the cards. **What’s new** shows the highlights of the newest release, marked when you have not seen them, then earlier releases in brief; the full version history is available from there. The Command Palette also exposes **Logline: Open Guide** and **Logline: What’s New**. Help gets a small **New** badge after an update, and the guide never opens by itself.

The top row of the Logs panel holds the tabs, **Logs**, **Analyze**, **Compare**, **Traces**, **AI calls**, **Metrics**, and **Issues**, with **Share with agent** and **More actions** (⋯) on the right. Each tab shows its view in place of the table. **Compare** appears once there is a production run to compare against, **AI calls** and **Metrics** while the OpenTelemetry receiver runs or once a service has sent LLM calls or metrics, and **Issues** while log doctor is on; tabs show their counts, and the panel reopens on the tab it was left on. Use the arrow keys to move between tabs.

On **Logs** and **Analyze**, the **Sources** rail on the left lists every source: under **Local**, terminals, saved commands, tasks, debug sessions, followed files, OpenTelemetry services, and imports, and under **Connections**, the stores you connected, each with what it is doing, such as *Tailing · 1,024 logs*. A dot shows whether a source is running. Click a source to see only its logs; its runs appear under it, with **All runs** first. Pointing at a source, or selecting it, shows its actions in place of its count: **Run** for a saved command that is not running, **Stop** for one Logline can stop, and **Remove** (the trash icon). **+** beside **Connections** adds a connection. **Stop all** in the rail's header appears while anything Logline started is running or a connection is tailing. The **«** button collapses the rail to a strip of icons, whose tooltips name each source; it starts collapsed on narrow panels, and the choice is remembered. **Compare**, **Traces**, and **Metrics** have a rail of their own in the same place, which collapses with it. In the rail, the arrow keys move between sources and runs, and Delete removes the focused source.

The filter row beside the rail holds the search box, with its **Saved searches** icon and **Syntax** help, then **All levels**, **My changes**, **Live**, and the **Columns** icon. It applies to **Logs** and **Analyze**; Compare, Traces, Metrics, and AI calls have their own filters. On narrow panels, tabs and filters show only their icons and counts, and rows wrap instead of hiding controls.

The status bar at the bottom says how many logs match, pages through them, and shows news such as a finished import or a failure. On the right, each item does what it shows: **Capture** turns terminal capture on and off, **OpenTelemetry** starts and stops the receiver, **Sharing** (while you share) opens the Share panel, the memory meter opens how many logs were received, kept, discarded, and cut short, with a link to the limits, and the check mark opens **Status and troubleshooting**. **More actions** holds **Copy filtered results**, **Export logs…**, **Import logs…**, **Clear logs**, **Break on matching logs**, **Manage servers…**, **Settings**, and **Help**.

Run **Logline: Run Command**, or open **Manage servers** in the Logs panel to add, edit, and delete saved commands. Multiple servers can run concurrently, each as a source in the rail. A selected source lists its runs, the individual command executions, with a **Stop** action beside each active run Logline or VS Code tasks own. **Stop** on a source stops its running commands, and **Stop all** stops every Logline-owned process and task. Externally captured terminal commands can be removed but not stopped by Logline. Running a command requires a trusted workspace.

**Remove** on a source drops its retained logs and runs. One that Logline is running is stopped first, after it asks, since that cannot be undone. A saved server command stays in `logline.servers`, so it can run again, and a source that keeps sending logs, such as an OpenTelemetry service, comes back with its next log. A shared source leaves a share of selected runs; sharing ends when nothing selected is left. On a connection, **Remove** asks first, since it removes the connection from settings and can forget its password or keys.

A saved server can also start automatically when the extension activates by setting `autoStart: true` on it (also requires a trusted workspace). Set `jsonOnly: true` on a server whose command interleaves build-tool output with its own JSON logs (for example `gradle bootRun`) to discard everything that isn't valid JSON.

Click **Capture off** in the Logs status bar so it reads **Capture on** (or run **Logline: Enable Terminal Capture**) to observe new commands in supported VS Code terminals. Capture starts at the next shell-integrated command; terminal scrollback from commands that were already running is not recoverable. Terminal output is stored as one `terminal` stream because the shell integration API does not expose stdout and stderr separately. Structured JSON levels remain authoritative; unstructured lines use an explicit leading level marker when present and otherwise appear as **Unclassified**. Capture is local and does not transmit logs by itself. Click **Capture on** again to turn it off at any time without stopping a terminal command.

Run **Logline: Follow Log File** to tail one or more local files, like `tail -F`. Logline shows the last 64 KiB of existing content, starting at a whole line, then every line appended afterwards. Following continues when the file is truncated, rewritten, or rotated (the path names a new file), and a file that does not exist yet is picked up once it is created. Each file appears as its own source; use **Stop** on the file's run or source, or **Stop all**, to stop following. Plain-text file lines get the same leading-severity detection as terminal output. Followed files are already on disk, so they are not copied to `latest.log`.

Output from **Docker Compose** and **Kubernetes** keeps its structure. Compose prefixes every line with its container (`api-1  | {"level":"error",…}`), and `kubectl logs --prefix` with the pod and container (`[pod/api-7d9f/api] …`). Logline splits off the prefix, so the payload is parsed like any other line: JSON and logfmt keep their level and fields. Each service becomes its own source (named after the service, such as **api**), stack traces are joined per container even when services interleave, and the full container name is kept in a `container` field (and `pod` for Kubernetes) for searching. A Docker timestamp printed by `--timestamps` becomes the event time when the payload has none. This works for commands you run with Logline, captured terminals, followed files, and imported `.log`/`.txt` files. **Logline: Follow Docker Compose Project** picks a `compose.yaml` or `docker-compose.yml` in the workspace and runs `docker compose logs --follow --timestamps` for it, which attaches to running services without starting them. Lines without a prefix (such as `Attaching to api-1, db-1`) stay in the source that printed them, and a container source shares that source's runs. Text that only looks similar, such as `a | b`, is left alone: Compose prefixes need a replica number. Set `logline.containerPrefixes` to `off` to keep prefixes in the message.

Program output from **debug sessions** (Run and Debug, F5) is captured automatically for every debugger, such as Node.js, Python, Java, Go, .NET, and C++. Logline reads the Debug Adapter Protocol output events that feed the Debug Console, so nothing in your launch configuration changes. Each launch configuration is a source named **Debug · <name>**, and each debug session is a run; child sessions (such as js-debug's per-process sessions) belong to their top-level configuration. Program `stdout` and `stderr` keep their streams, and debugger messages appear as the `console` stream. Use **Stop** on the session's run or source to end the debug session; **Stop all** leaves debug sessions running because VS Code owns them. When a debugger reports where a line was logged (js-debug does for `console.log`), the expanded event offers **Open code**. Debug capture records what the Debug Console shows. A launch configuration with `"console": "integratedTerminal"` (the default for Python and Java) sends program output to a terminal instead, so only debugger messages reach the Debug Console; turn on **Terminal capture** to record that output, or set `"console": "internalConsole"`. While terminal capture is on, such debug sessions are skipped so lines are not recorded twice. Turn debug capture off with `logline.captureDebugSessions`.

Use **Logline: Manage Terminal Capture** to ignore or re-enable a terminal for the lifetime of that terminal instance. Full-screen alternate-screen applications are skipped; run the command again in a regular shell to capture it.

Choose **Share with agent** in the top row to make all retained Logline sources and new runs in this VS Code window available to agents (Copilot, and Claude Code, Codex, or other MCP clients you connected), regardless of the current source, run, or search filters. The first use shows a confirmation explaining the scope and that common credentials are redacted but logs may still contain sensitive information. Accepting **Share logs** remembers that confirmation on this VS Code profile; later uses enable sharing immediately. Cancelling or choosing **Choose specific runs…** does not remember acceptance. You can enable sharing before any logs have arrived.

The button shows **Sharing · Stop** (only its highlighted icon on narrow panels), and the status bar describes the scope. Click the button to revoke access. Sharing itself is held in memory and ends when logs are cleared or the window or workspace changes; it is never restored automatically.

The arrow beside the button opens the **Share** panel. **What agents can read** is **Everything captured in this window** or **Specific runs** (or **Logline: Choose Specific Runs to Share with Agent**), which asks which runs to share. **Agents** lists GitHub Copilot, Claude Code, and Codex with whether each can read what you share: *Ready*, *Connected*, *Reading* (it read shared logs in the last few minutes), or **Connect…**, which sets that agent up as below. **Production access** lists your connections with a log table, each with **Allow** for agents to fetch from it (see [Agents and connections](#agents-and-connections)). The panel ends with **Status and troubleshooting…** and **Start sharing** or **Stop sharing**. Selected runs include continuing output, but later commands are excluded. Expanding an event also offers **Share with agent**, which grants only that event’s source and exact run. Cancelling the picker preserves the current sharing scope.

Agent tools respect the active sharing scope and are always redacted, even when export redaction is disabled. They can list shared sources and runs, search with bounded pagination, inspect one event with nearby context, analyze rates/errors/latency/status patterns, read one distributed trace (`logline_get_trace`; spans only from shared OpenTelemetry services), list LLM calls, tool executions, and agent runs with their tokens and, on request, the start of their conversations (`logline_get_ai_calls`), and wait briefly for fresh events after a reproduction. With a connection you allowed (see [Agents and connections](#agents-and-connections)), they can also fetch production logs into a run and compare it with your local runs. Searches, analysis, and waits take `changedOnly: true` to keep only events from code changed since the last commit, the same as **My changes**; their result's `changedFiles` says how many files changed, or `null` outside a git repository. Log content is untrusted application data; sharing does not allow an agent to run or stop commands. Continue in any Copilot agent chat in this window and ask it to inspect the shared logs. With the Logline tools enabled in chat, Copilot can discover the shared runs without a chat picker or handoff prompt. Sharing makes logs available on request; it does not send all logs into chat or send a chat message. The optional **Logline: Ask Copilot to Investigate Logs** command still opens an editable prompt.

### Claude Code, Codex, and other MCP clients

Claude Code, Codex, and other MCP clients use the same tools through Logline's MCP server. Run **Logline: Connect Claude Code or Codex** once and choose the agent, or choose **Connect…** beside the agent in the Share panel:

- **Cursor agent**, **Windsurf agent**, or **Kiro agent** appears first when Logline runs in that editor. It adds a `logline` server to the editor's user MCP file (`~/.cursor/mcp.json`, `~/.codeium/windsurf/mcp_config.json`, or `~/.kiro/settings/mcp.json`) and keeps the servers already there. The entry passes `--workspace ${workspaceFolder}` so the agent reads the logs of the project it has open; an editor that does not expand the variable falls back to the folder it starts the server in. A file that is not plain JSON is left alone, and the server entry is copied instead.
- **Claude Code** runs `claude mcp add … --scope user logline -- …`, so Logline is available in every project, in the terminal and in the Claude Code extension.
- **Codex** runs `codex mcp add logline …`. The Codex CLI, IDE extension, and app share this setting.
- **Other MCP client** copies a stdio server entry (`command`, `args`, `env`) to add to that client's configuration.

You can run the command in a terminal or copy it. Restart the agent afterwards so it loads Logline.

Connecting Claude Code or Codex also installs four skills: step-by-step investigations that use the Logline tools. Claude Code reads them from `~/.claude/skills` (or `$CLAUDE_CONFIG_DIR/skills`), and Codex from `~/.agents/skills`. The agent picks one when your request fits, or you can start one yourself: `/logline-verify` in Claude Code, `$logline-verify` in Codex.

| Skill | What the agent does |
| --- | --- |
| `logline-verify` | After a change, waits for fresh logs, searches errors from changed code (`changedOnly`), inspects them, and reports whether the change works, fails, or produced no evidence. |
| `logline-triage` | Groups errors with `logline_analyze_logs`, inspects the largest and newest groups, their traces, and any failed LLM or tool calls, and ranks what is failing with the likely cause and the code to change. |
| `logline-slow-request` | Reads latency percentiles, finds slow requests with a trace id, and uses trace hotspots, self time, and the tokens and duration of LLM calls to say where the time goes. |
| `logline-reproduce-prod` | Fetches a production failure from a connection you allowed, reproduces it in a local run, fixes it, and compares again until the error is fixed locally and nothing new comes from the change. |

Logline keeps installed skills up to date when it updates, and never adds them for an agent you did not connect. The MCP server also offers the same four workflows as prompts (`verify`, `triage`, `slow-request`, `reproduce-prod`), which clients that support MCP prompts list as commands, such as `/mcp__logline__triage` in Claude Code. The server runs with VS Code's own runtime, so Node.js does not need to be installed, and it lives at `~/.logline/mcp.js`, which Logline updates with the extension.

Agents read only what you share with **Share with agent**, always redacted, and **Sharing · Stop** cuts them off immediately. While sharing, the status bar shows which agents read the logs recently, for example *read by Claude Code*. Each VS Code window listens on `127.0.0.1` only and writes its port and a random token to `~/.logline/agents/`, readable only by your user; the MCP server forwards each tool call to the window whose workspace folder contains the agent's working directory. An agent started outside every window's workspace folders is refused, so an agent in one project cannot read logs shared from another; set `LOGLINE_WORKSPACE` to the folder of the window to use. Redaction hides values under sensitive keys and credentials recognizable on their own, such as GitHub, AWS, Slack and Stripe keys, JSON Web Tokens, bearer tokens, private keys, and passwords in URLs. Set `logline.externalAgents` to `false` to stop accepting MCP clients.

**Live** follows the newest events automatically, with the newest at the top. Scrolling down to read leaves Live, so new rows do not push what you are reading; the status bar says when newer logs have arrived, and scrolling back to the top (or choosing **Live**) resumes it. Set `logline.newestFirst` to `false` for terminal order, with the newest at the bottom. Turn Live off to browse retained history with the status bar's page arrows. Sorting switches to Browse; returning to Live (or Resume after inspecting an event) clears the sort and expanded event and jumps to the newest rows in capture order. The panel renders up to **1,000 rows per page**.

While an event is expanded, incoming logs leave the inspected rows alone. Changing filters, paging, sorting, or selecting columns closes inspection and refreshes the results in Browse mode. Choose Live to follow new events again.

Saved server commands and ad-hoc commands run through the platform's default shell; tasks can select literal argument mode. Stop sends SIGTERM to the process group on macOS/Linux, escalating to SIGKILL after two seconds. Windows uses `taskkill /T /F` to stop the process tree immediately. Changes to `source` and `maxLineLength` apply to newly started processes; restart an existing process to change its capture settings.

## Import and export

Choose a source in the rail, and one of its runs to narrow it to one command. Completed terminal runs remain selectable while their events are retained, while empty completed terminal metadata is removed automatically. Use **More actions → Export logs…** to save the current source, run, search, and level filters as JSON Lines, JSON, CSV, or **AI context (Markdown)**, with redaction enabled by default. The AI context option and **Copy filtered results** include the latest 1,000 matching events in capture order. **More actions → Import logs…** loads JSON, JSONL, CSV, and plain-text log files into a separate `Imported · filename` source for offline searching. A CSV exported by Logline replays its `raw` payloads; imported events receive new IDs, an import stream, and a new session. Other CSV rows use their header names as fields, or replay a nonempty `raw` cell when present.

JSON and JSONL exports contain Logline event envelopes, including normalized metadata and `raw`. Import currently treats these envelopes as new JSON payloads; use CSV to replay the original raw records. Plain-text records without their own timestamps receive the import time.

Full JSON, JSONL, and CSV exports take a fixed snapshot after you choose a destination, then redact and write records in batches. Cancel through the progress notification. Local files are replaced only after the export completes; cancellation or failure preserves an existing destination. CSV includes the first 200 distinct payload fields encountered in capture order, sorted as columns, plus the standard metadata and full `raw` payload. Filesystem providers that require a whole-file write are limited to 16 MiB; use a local file or a narrower filter for larger exports. Small context and Markdown exports use the regular save flow.

Local imports stream records in batches so capture and panel interactions can continue. Use `.json` for JSON documents (including arrays and multiline objects), `.jsonl`/`.ndjson` for one JSON event per line, and `.log`/`.txt` for mixed line-based output. Imported records share the `maxLineLength` limit with live capture; oversized records are marked truncated and the next record is still imported. CSV records support quoted multiline cells. Non-file VS Code filesystem providers require a whole-file read, followed by incremental processing.

## Search and filters

The level filter (next to the search box) is a multi-select — check any combination of Trace/Debug/Info/Warn/Error/Fatal/Unclassified. Click **Syntax** in the search box for a reference to the query syntax below.

Search supports Datadog-style queries:

- Field filters — `level:error`, `service:api`
- Quoted phrases, negation, and OR — `"database timeout" -service:web`, `service:web OR service:api`
- Wildcards and exact match — `status:5xx`, `status:503`
- Comparisons and ranges — `duration:>200`, `status:[500 TO 599]`
- Field presence — `exists:requestId`
- Regex — `message:/timeout/i`
- Relative or absolute time — `last:15m`, `timestamp:[2026-01-01 TO 2026-01-02]`
- Code changed since the last commit — `changed:true`

A term becomes a field filter when a bare identifier precedes the colon. URLs such as `http://api/health` and clock times such as `12:30:05` are free text. Quote an entire `host:port` value, such as `"localhost:3000"`, to prevent it being interpreted as a field filter. Ordinary text matching ignores case; regex patterns preserve case and escapes, and use the `i` flag for case-insensitive matching.

### Logs from your changes

`changed:true` keeps events that came from code you changed since the last commit, staged or not: the log statement that wrote the event, the code location the event reports (such as a debugger's location or a `caller` field), or a stack frame in its exception is on a changed line. A new, untracked file counts as changed throughout. In a git repository, **My changes** next to the level filter turns it on and off, adding `changed:true` to every `OR` branch; its tooltip shows how many files changed. Combine it with anything else, for example `level:error changed:true` for the errors your edits caused, and use it in **Analyze**, exports, saved searches, and **Break on matching logs**. `-changed:true` hides them instead. Edits count once the file is saved or changes on disk, including files an agent or formatter rewrote, and a commit resets the comparison. In a working tree with more than 300 changed files, only the first 300 are compared.

Changed lines come from VS Code's built-in Git extension. A file is compared with `HEAD` when it first shows as changed and again each time you save it; a commit, checkout, or reset compares everything again. Up to 300 changed files are compared. An event only matches when it can be tied to a line: a message must match an indexed log statement (log lenses must be on), and stack frames must name source files rather than compiled output without source maps. `changed:` with any value other than `true` or `false` searches a field named `changed` as usual.

Field names match as typed and fall back to common aliases, so `statusCode:200` and `status:200` both work whether the log calls the field `status` or `statusCode`. The same holds for `level`/`severity`, `message`/`msg`, `service`/`service_name`, `requestId`/`request_id`, `traceId`/`trace_id`, and `durationMs`/`duration`.

Right-click a table cell to **Include value** or **Exclude value** in the current search. The menu shows the field and value, preserves quotes and whitespace, and applies the condition to every `OR` branch. Matching follows the normal search rules (usually case-insensitive contains matching, with special handling for status codes). Server and level selections remain active. Missing or empty values, unsupported field names, and actions that would exceed the 256-character search limit are disabled with an explanation.

Applied search terms appear as removable chips inside the search control. Type a term and press Enter to add it; click a chip to edit it or use its **×** button to remove it. Use **Clear all filters** to remove every query term while keeping server and level selections.

For keyboard access, Tab into a table cell, use arrow keys to move between rendered cells, and press **Shift+F10** to open its menu. Use Up/Down and Enter to choose an action; Escape returns focus to the cell. Applying a filter while inspecting an event returns to Browse. Menus close when the table scrolls or its displayed rows are replaced.

The bookmark icon in the search box opens **Saved searches**, the icon at the end of the filter row opens **Columns**, and the **Analyze** tab charts the current filter. **Saved searches** stores up to 50 named combinations of query, server, and levels, including level-only filters. Saving the same combination replaces its previous entry; use its × button to delete it. There is no automatic recent-search history. While typing, field names and common values are suggested for the field-query syntax used by search.

Autocomplete preserves preceding terms and quotes suggested values, including spaces, quotes, and backslashes. Suggestions for older input or a previously selected server are ignored.

## Columns and log formats

Automatic columns use fields from the selected server, recognize common aliases, and fall back to custom JSON fields instead of showing no payload columns. **Columns** offers up to 200 retained payload fields, including nested dotted paths, so you can add fields beyond the six automatic choices. Added columns are saved with the webview state. Explicit `logline.columns` settings also resolve common aliases.

Format handling covers [ECS](https://www.elastic.co/docs/reference/ecs/logging/nodejs/winston) dotted or nested fields such as `service.name`, `log.level`, `@timestamp`, and `http.response.status_code`; [Pino HTTP](https://github.com/pinojs/pino-std-serializers) request/response fields; and individual [OpenTelemetry log records](https://opentelemetry.io/docs/specs/otel/logs/data-model/) with severity, body, typed attributes, and nanosecond timestamps. Full OTLP batch envelopes and arbitrary arrays are available in event details rather than expanded into table columns.

Plain-text lines in [logfmt](https://brandur.org/logfmt), such as `time=2026-10-03T10:00:00Z level=warn msg="slow query" durationMs=212`, become structured events: `level`, `msg`, and `time` work as they do in JSON, and the remaining keys become searchable, sortable fields. Pure numbers are stored as numbers, so `durationMs:>200` works. A line counts as logfmt only when every token is a `key=value` pair and there are at least two pairs, so ordinary text containing `=` stays plain text.

Log4j2 JsonLayout output is supported directly: the `timeMillis` field is read as the event timestamp, and MDC values nested under `contextMap` are flattened so they're searchable like any other field.

The timezone setting supports Local and UTC.

Click a column's name to sort by that field and click it again to reverse the direction; the arrow shows the active direction. Drag its grip to rearrange columns, or drag the divider at its right edge to resize. Payload fields also have an `×` remove control, and **Columns** restores them. Column widths and order are saved per webview. Rows keep a single-line preview; expand an event to read its full contents. Scrolling past an expanded event preserves its details and internal scroll position.

## Analysis

**Analyze** summarizes the retained logs that match the current filter, on the same rail and filter row as **Logs**: tiles for how many logs, how many are errors (with their share), p95 latency (with its peak and when, or p50 and p99), and how many error groups there are and how many are new; volume over time stacked by level (errors, warnings, and the rest), with unusual spikes marked; error groups beside latency over time; status codes; the most common values of fields such as source, service, and path; error groups; and the top 20 log patterns, shown with their variable parts as `*` (`POST * completed in *`). Patterns and error groups show their share, a trend over the range, and a **New** badge when they first appeared in its last quarter. Error groups also show where the error was thrown and when it was first and last seen.

Everything is a way into the logs: click a bar to filter to its time range, or drag across bars to select a window and choose **Show in Logs**, a status code or field value to filter to it, a source to select it, or a pattern or error group to filter to its messages. The filter is added to the current search. Numbers with units (`48ms`, `1.5s`) and ids do not split a message into separate patterns, and an error logged both with and without its stack is one group. A few events with timestamps far from the rest, such as plain lines stamped on arrival among replayed logs, are left out of the time charts and noted, but still count everywhere else. Analysis uses only events currently retained in memory.

## Exceptions and surrounding context

Expand an event to read structured exceptions as stack frames with real line breaks and nested causes. Common `err`, `error`, `exception`, `thrown`, and stack fields are supported, including Log4j2 throwable frames and OpenTelemetry exception fields. Click a stack frame to open its source location in the workspace; ambiguous filenames open a file picker. **Original event** keeps the JSON available, and **Copy** copies the original formatted event. Plain-text stack traces are joined into one event: Java and Node `at` frames, `Caused by:`/`Suppressed:` sections, `... N more` lines, and Python tracebacks (including chained ones) attach to the line before them. An uncaught Node.js crash is joined as one block: the `path:line` header, the source line and caret, the error, its frames and properties, and the `Node.js v…` line. The row shows the first line (the error line for a Node crash), and a trace headed by an exception without a leading severity is an error; expanding it shows every frame with source links, and error grouping uses the originating frame. A line is held briefly (100 ms) to see whether frames follow it, and JSON lines are never held or joined. When a plain-text crash or stack trace follows a JSON error from the same source and run, within 2 seconds (30 seconds for a Node crash ending in `Node.js v…`, which Node prints as the process exits) and with no other JSON line between them, the two are linked: the error's details show the crash's stack with source links, and the crash row and its details lead back to the error. Both stay separate events in capture order, so search, export, redaction and the persisted log see them exactly as captured; agents inspecting the error receive the crash too, redacted on its own. Imported files are not linked. Turn this off with `logline.joinStackTraces`.

Rows show what they link to: a code icon when Logline knows the log statement behind the event (click it to open the statement), a trace icon when the event has a trace id, and a log doctor icon when the statement has a finding (click it to open the event and read the finding). Hover over a row for icon buttons at the end of its message: **Surrounding logs**, **Trace**, **Open code**, and **Break here**, without expanding it. While **Live**, new rows are held while the pointer moves over the table, so rows do not shift while you aim at one. They appear two seconds after the pointer stops moving, or as soon as it leaves the table.

Choose **Surrounding logs** on an expanded event to see up to 25 retained events before and after it, in capture order, from the same command run. Context includes all levels and both captured streams, regardless of the current search. Select any surrounding event to inspect its details. **Back to results** (or Escape) returns to the existing search and scroll position. Context is a fixed snapshot; ingestion continues, and discarded events cannot be recovered. Each newly imported file has its own context boundary.

## OpenTelemetry and traces

Click **OpenTelemetry** in the status bar (or run **Logline: Start OpenTelemetry Receiver**) to receive telemetry from instrumented apps on this machine, without running a collector, Jaeger, or another backend. Logline listens for OTLP/HTTP on `127.0.0.1:4318` (`logline.otlp.port`). It accepts `application/json` and `application/x-protobuf` on `/v1/logs`, `/v1/traces`, and `/v1/metrics`, with optional gzip or deflate compression. Requests over 1 MiB are decoded on a worker thread, and large batches are added in steps, so a big export does not stall the editor. If another collector already uses the port, Logline listens on a free port instead and says so; it never takes over a port in use. Start and Stop apply to the current window and do not change settings; set `logline.otlp.enabled` to start the receiver automatically, and changing that setting takes over from Start and Stop. The receiver only binds to loopback and refuses requests that carry a browser `Origin` or a non-loopback `Host` header, so web pages cannot send it telemetry.

While the receiver runs and `logline.otlp.injectEnvironment` is on, new processes are pointed at it with standard SDK variables: `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf`, `OTEL_TRACES_EXPORTER=otlp`, `OTEL_LOGS_EXPORTER=otlp`, `OTEL_METRICS_EXPORTER=otlp`, shorter batch delays so telemetry appears within a second, and `OTEL_METRIC_EXPORT_INTERVAL=5000` so metrics arrive every 5 seconds instead of every minute. This applies to Logline servers and tasks (which also get `OTEL_SERVICE_NAME` from their label), debug launch configurations, and new VS Code terminals. If an environment already chooses an exporter destination (any `OTEL_EXPORTER_OTLP_*ENDPOINT`, `OTEL_TRACES_EXPORTER`, `OTEL_LOGS_EXPORTER`, `OTEL_METRICS_EXPORTER`, or `OTEL_SDK_DISABLED`), Logline adds nothing; otherwise it only adds variables that are not already set. Terminals that were open before the receiver started keep their old environment; VS Code marks them so you can relaunch them.

Each service that sends telemetry appears as a source named **OTel · <service.name>**. Log records become events with `service`, `traceId`, `spanId`, severity, scope, resource attributes (under `resource.`), and their own attributes as searchable fields; an attribute whose name collides with a Logline field is kept as `attributes.<name>`. Exception attributes (`exception.type`, `exception.message`, `exception.stacktrace`) appear as readable stack traces, and `code.filepath`/`code.lineno` link to the log statement. Spans are kept for trace views (up to 20,000 spans or about 64 MiB, oldest first out). `logline.otlp.showSpans` also adds rows for spans: `entry` (the default) shows trace roots and incoming server or consumer spans, such as `GET /orders/:id (182 ms)`, with `durationMs`, `spanKind`, `spanStatus`, and span attributes as fields, so `durationMs:>200` and **Analyze** latency work on requests. `all` shows every span and `none` keeps spans out of the table.

Open the **Traces** tab to see recent requests: each trace's start time, root operation, services, duration (as a bar scaled to the slowest trace), and how many spans and logs it has. Traces with errors are marked in red. The rail beside the list has each service, with its color and how many traces it is in: uncheck a service to leave out traces that only pass through hidden services. Below them, **Only traces with errors** and **Slower than 1 s** narrow the list. Choosing a trace opens its waterfall below the list, so another trace can be chosen from there, and **Close** hides it. The list includes traces that only appear in logs, such as JSON logs with a `traceId`, so it is useful without OpenTelemetry too. The tab shows how many traces with spans are retained, and while the receiver runs the **OpenTelemetry** item in the status bar shows its address with a green dot; click it to stop the receiver. In the table, rows that belong to a trace have a trace button next to the message that opens its waterfall in one click.

The **Metrics** tab appears while the OpenTelemetry receiver runs or once a service has sent metrics, with the number of series. Each series (a metric name, its service, and its attributes) is a card with its latest value and a trend line of recent points (up to 120 are kept per series, and the trend line shows up to 60 spread over them), most recently updated first; type in the filter to narrow by name, service, or attribute, or choose a service in the rail beside the cards. Choosing a card charts its series larger above the cards, with everything known about its latest point; choosing it again closes the chart. The rail also lists your connections: choosing one sets it in the metric query bar. What a series shows depends on its kind: gauges and up-down counters show their value; counters show a rate per second, with the running total in the tooltip; histograms show the p95 of the values recorded since the previous export, estimated from their buckets, with p50, average, minimum, and maximum in the tooltip; and summaries show their 0.95 quantile. A counter that restarts is measured from its new start. Values are shown in the metric's unit, such as `ms`, `s`, or `By`. Up to 2,000 series are kept, the least recently updated going first, and **Clear logs** removes them. While shown, the list refreshes as new points arrive, at most once every 5 seconds.

The **AI calls** tab appears while the OpenTelemetry receiver runs, saying how to send calls until some arrive, and stays while calls are retained. It lists spans that follow the OpenTelemetry GenAI semantic conventions: LLM calls (`chat`, `text_completion`, `generate_content`, `embeddings`), tool executions (`execute_tool`), and agent runs (`invoke_agent`). Its totals show model calls, input and output tokens with the share of input tokens served from the provider's cache, p50 and p95 model latency, and tool calls, followed by a table per model with its provider, calls, tokens, p95, and errors; choose a model to list only its calls, and choose it again to list every call. The list shows each call's start time, operation and model or tool, agent, tokens in → out, duration, and why the model stopped. A failed call is red, and a response cut short by a token limit or a content filter (`length`, `max_tokens`, `content_filter`) is marked as a warning. Filter by model, tool, agent, or service, show only model calls, tool calls, or agent runs, or only failures. Up to 500 of the newest calls are listed while the totals cover every retained one, and a shown list refreshes at most every 5 seconds.

Choose a call to read its conversation: the system instructions (collapsed), the input messages, and the response, with reasoning, tool calls and their arguments, and tool results. Each tool call shows how its `execute_tool` span went, its duration, and its result, matched by the tool call id. The tools offered to the model are listed, collapsed, at the end. **Previous** and **Next** step through the calls of the same conversation (`gen_ai.conversation.id`, or else the same trace), **Trace** opens the call's trace, and **Copy** copies the conversation as Markdown, redacted like exports when `logline.redactExports` is on. Parts longer than 16 KB show their first 16 KB. In the trace waterfall, GenAI spans carry a chip marked with the AI calls icon; choose it to open the call. A model call's chip shows its tokens, an agent run's the model calls beneath it and their tokens, and any chip the model or tool when the span name leaves it out.

SDKs record prompts and responses only when content capture is on, for example with `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT=true`; without it, a call shows its model, tokens, timing, and outcome, and says it has no content. Logline reads messages from `gen_ai.input.messages`, `gen_ai.output.messages`, `gen_ai.system_instructions`, and `gen_ai.tool.definitions`, recorded either structured or as JSON text, and also from the forms older instrumentations emit: `gen_ai.system` and `gen_ai.usage.prompt_tokens` / `completion_tokens`, OpenLLMetry's `gen_ai.prompt.<n>.*` and `gen_ai.completion.<n>.*` attributes, and `gen_ai.*.message` and `gen_ai.choice` span events. These content attributes, and the content of GenAI message events, keep up to 64 KiB each on spans, instead of the 4 KiB other attributes and log records keep, and they stay out of span rows in the table and the waterfall's tooltips. To try it, run the [checkout sample](../samples/README.md#checkout-demo), whose support assistant records an agent run for each declined order, or start the receiver and send [samples/genai-trace.json](../samples/genai-trace.json): `curl -X POST -H 'Content-Type: application/json' --data @samples/genai-trace.json http://127.0.0.1:4318/v1/traces`.

Expand any event that has a trace id (from OpenTelemetry or from a JSON log's `traceId`/`trace_id` field) and choose **Trace**. Events without a trace id show **Trace** disabled, with the reason in its tooltip. You can also run **Logline: Show Trace** with an id. The trace view is a waterfall of every received span across services, indented by parent, with failed spans in red and the critical path (the chain of spans that determined when the request finished) highlighted. **Self** is the time a span spent itself: its duration less the time its child spans cover, with overlapping children counted once and time outside the span ignored. A span with a large duration and little self time was waiting on its children; one with a large self time was doing the work, or waiting on something it did not trace. **Where the time went**, above the waterfall, ranks up to 8 operations (grouped by service and name, across every span of the trace, including those beyond the display limit) by total self time, with their span count and share of all self time; choose one to scroll to its first span. Hover over an operation to see its attributes and events. Retained logs with the same trace id appear under their span, or in a separate list when they name no received span; click one to open its surrounding logs. Logs from processes that only print JSON with a trace id are included too, so services that log to stdout and services that export over OTLP join up. **Filter logs by trace** applies `traceId:<id>` to the table. **Clear logs** removes spans as well as events. With `logline.persistLogs`, received log records and span rows are written to `latest.log` as the JSON lines shown in the table.

## Connections: Datadog, Postgres, MySQL, MongoDB, and SQLite

Logline can search and tail logs kept outside the editor, next to the runs you capture locally: logs in a Datadog organization, the log table of a SQLite file or a Postgres or MySQL server (Aurora and RDS included), and a log collection in MongoDB. Every connection is read-only.

Run **Logline: Add Connection**, or choose **+** beside **Connections** in the Sources rail. Pick SQLite and the database file, or Postgres and a connection URL such as `postgres://dev@localhost:5432/orders` (`?sslmode=require` turns on TLS with certificate checks). Logline connects, then lists the tables: choose the one with one row per log event, or **No log table** to only run SQL you type. It suggests which columns hold the time, level, message, service, and trace id from their names (`created_at`, `severity`, `msg`, `app`, `trace_id`, and similar); choose a role to change its column. The time column is required. It can be a date/time type, ISO 8601 text (text without a zone, like SQLite's `CURRENT_TIMESTAMP`, is read as UTC), or seconds or milliseconds since 1970, which is detected from a sample. Every other column becomes a searchable field. The connection is saved in `logline.connections` in the workspace settings, with a SQLite path inside the workspace saved relative to it. A password, typed or in the URL, is kept in VS Code secret storage and never in settings; Postgres connections to the same user, host, port, and database share it across workspaces. If Postgres refuses the login later, the error offers **Enter Password…**.

Choose the connection in the Sources rail (it is listed under **Connections** before it has any runs) to show its controls under the search box: a time range from the last 15 minutes to the last 7 days, **Run**, **Tail**, and **Run SQL…**. Nothing is fetched until you press **Run**. The filters in the search box become SQL: free text matches any column, `field:value` matches a column of that name, or the mapped column for `level`, `message`, `service`, and `traceId`, as a case-insensitive substring; numeric comparisons and ranges apply to numeric columns; `status:5xx`, `exists:`, negated field terms, `OR`, `last:`, and `timestamp:[…]` are translated too. Values are always sent as query parameters. A line under the controls shows the SQL a search runs as, and which terms only Logline can apply, such as regular expressions, `changed:`, negated free text, and fields the table does not have: Logline fetches the rows the rest of the search allows and applies those terms itself, so a fetch can bring back more rows than match, never fewer. A search reads the newest `logline.connectionMaxRows` (5,000) matching rows in the range. The result line says how many rows came back, out of how many matched in the range when the limit cut it short, how many match the whole search, and how long the query took.

Each **Run** is a new run under the connection's source, named by its search and range, and the panel switches to it; earlier results stay as runs under the connection in the rail, and **All runs** shows them together. Fetched rows are events like any other: search, **Analyze**, traces, export, sharing with agents, and **Clear logs** all apply, and they are never written to `latest.log`. **Tail** shows the newest 200 matching rows, then reads rows added since every `logline.connectionPollSeconds` (2) seconds; a row already shown is not shown again. When more rows arrive between reads than `logline.connectionMaxRows`, the next read continues from the last row read until the tail catches up. If a read fails, for example while the database is locked, the result line says **Tail interrupted** and the tail keeps trying. Press **Stop tail**, or stop its run, to end it. **Run SQL…** runs one `SELECT`, `WITH`, or `VALUES` query you type and keeps up to `logline.connectionMaxRows` rows in the order it returns them. The search box is cleared, since the query chose the rows. Columns named like a time, level, or message, or the mapped columns, are read as those.

Every query is read-only: SQLite files are opened read-only, and each Postgres query runs in a read-only transaction. Postgres `timestamp` and `date` values, which have no time zone, are read as UTC, and searches compare them as UTC. A query that runs longer than `logline.connectionTimeoutSeconds` (10) is stopped. SQLite queries run in a separate process, so a slow one never blocks the editor. Logline uses the SQLite built into the editor's runtime, which current VS Code versions have; editors without it use the `sqlite3` command (3.33 or later) from your PATH. Connections need a trusted workspace. The Command Palette also has **Search Connection…**, **Run SQL on Connection…**, **Start or Stop Tailing Connection**, **Test Connection**, and **Remove Connection…**. Passwords are kept by the server, user, and database they open, so other workspaces connecting there share them; removing a connection keeps the password unless you choose **Remove and Forget Password**.

### Datadog

Choose **Datadog** in **Add Connection**, then your site (the domain of your Datadog web app, such as `datadoghq.com` or `datadoghq.eu`, or **Other…** for an https API URL such as a proxy), and how Logline signs in: an API key and an application key, or an access token. They need the `logs_read_data` permission, are kept in VS Code secret storage under the API's address, and are never written to settings; if Datadog refuses them later, the error offers **Enter Keys…**. Logline checks them with a one-log search before saving the connection as **Datadog · <name>**. Set `indexes` on the connection in settings to search only some log indexes.

A Datadog connection has the same **Run** and **Tail** as a database, without **Run SQL…**. The search box's filters become Datadog search syntax, shown under the controls: `level:` becomes `status:` (a part of a level matches, so `level:warn` also finds `warning`), `service:`, `host:`, and `traceId:` use Datadog's reserved attributes, `status:5xx` and other HTTP statuses become `@http.status_code`, other fields become `@` attributes matched anywhere in their value, words and phrases are searched in the message and every attribute (`*:*word*`), and `message:` terms only in the message. Values keep the case you type, since Datadog compares attribute values with case. Regular expressions and `changed:` are applied by Logline to the logs Datadog returns. A search reads the newest matching logs in the range, up to `logline.connectionMaxRows`, in pages of 1,000, and counts every match with one more request when the limit cuts it short. Each log becomes an event with its time, status, message, service, host, trace id, tags, `datadog.id`, and its attributes as fields; an attribute named like one of those is kept as `attributes.<name>`. A tail reads back a minute each time, because Datadog can take that long to make a log searchable, and shows each log once. Datadog limits how often an organization can search logs, so a Datadog tail reads at most every 15 seconds, whatever `logline.connectionPollSeconds` says, and when Datadog answers that the limit was reached, it waits as long as Datadog asks before reading again.

**Open link…** (or **Logline: Open Datadog Link or Trace ID…**) takes a Log Explorer link and fetches its search over its time range as a run; when the link points at a log with a trace id, a second run fetches every log of that trace from half an hour around it, and the panel switches to it. Paste a trace id instead to fetch that trace from the last day. The search box is cleared, so every log the link fetched shows.

### Metrics from connections

While a connection is saved, the **Metrics** tab has a **Metric query** bar above its list. Choose the connection, type a query, choose a range, and press **Run** or Enter. For Datadog, the query is a metric query such as `avg:trace.http.request.duration{service:checkout} by {env}`, and metric names that reported in the last day are suggested as you type the first word; it needs the `timeseries_query` and `metrics_read` permissions. For a database, it is a `SELECT` that returns a time column, a value column (named `value`, else the first numeric one), and optionally text columns that name the series, such as `SELECT minute AS time, avg(duration_ms) AS value, service FROM requests GROUP BY 1, 3`; it runs read-only, and the database returns only the rows in the range, up to 50,000, newest first. Each query is its own metric, named by its text, so two watched queries on one connection stay apart.

The chart shows up to 20 series of up to 300 points each, with the value axis in the metric's unit and a legend with each series' latest value. Hover to see every series' value at that time. Drag across a spike to select that window: **Show logs from <connection>** fetches the connection's logs from exactly that window, with the Logs tab's filter, as a new run, and **Local logs** filters your local runs to the same window. **Watch** keeps reading the query every 15 seconds into the Metrics list below, as series of the connection's service, so it trends next to OpenTelemetry metrics (each read covers the last 10 minutes, so a series appears once it has a point in that time); press **Stop watching** to end it.

### Agents and connections

Agents never reach a connection on their own: sharing logs with **Share with agent** covers the runs you fetched, not the store behind them. To let agents fetch, choose **Allow agents** under a connection's controls (or **Logline: Allow Agents to Query Connection…**) and confirm. The permission is kept for the database or API the connection opens, in VS Code's own storage rather than settings, so a workspace cannot grant it; **Agents allowed** or **Logline: Stop Agents Querying Connection…** takes it back.

With a share active, `logline_list_shared_sources` lists the connections and whether agents may query each. `logline_fetch_production` takes a Logline search or a trace id and a range of at most 24 hours, fetches up to 1,000 logs into a run named **Agent: …** under the connection's source, adds it to the share, and returns the run id and its top error groups rather than the logs, which the agent then reads with the other tools. Each connection allows 10 fetches a minute. `logline_compare_with_production` compares that run with a shared local source's newest shared runs, like the Compare tab (a run that starts after you share selected runs is not included until you share it), so an agent can confirm it reproduced a failure and that its fix removed it. Results are redacted, and Copilot asks before each fetch, naming the connection and range.

### Compare production with local runs

The **Compare** tab answers two questions while you debug a production failure: does my local run reproduce it, and does my fix make it go away? It appears once there is a production run to compare against: a run fetched from a connection, or an imported log file. Choose **Compare with local** under a connection's controls (it compares the selected run, or the latest), or open the tab and choose **Production** and **Local** in its header: the source you run locally, such as your app or your tests. The newest local source is chosen by default. The rail beside the table shows **All errors** or those of one status, with how many each has, and **From your changes** keeps only errors thrown from code changed since the last commit.

Each row is one error, matched between the two sides by its message with ids, numbers, and paths masked, because file paths and line numbers differ between machines and move when the code changes. The row shows how often it occurred in production and in each of the local source's three newest runs, and its status: **Reproduced** (in production and the newest run), **Fixed locally** (in production and an earlier run, but not the newest), **Not seen locally**, **New** (only in the newest run), or **Local only**. A new error thrown from code changed since the last commit is marked **changed** with its file and line, since your change most likely caused it. Choose a row to see an event from each side in the panel beside the table, with the fields whose values differ highlighted, and **Surrounding logs** to open either one in context. The tab refreshes while new output arrives. When a run of the compared local source finishes, a notification says what it did, such as *1 production error fixed locally · 1 new local error from your changes*, with **Show Comparison**.

## Log statements in the editor

Logline indexes logging calls in workspace source files: calls such as `logger.info(...)`, `console.error(...)`, `log.Printf(...)`, `slog.Info(...)`, `_logger.LogInformation(...)`, `print(...)`, or Rust's `info!(...)` whose message is a string literal, in JavaScript, TypeScript, Python, Java, Kotlin, Scala, Groovy, Go, C#, Rust, Ruby, PHP, Swift, Dart, and C/C++ files. The message can be the first argument, or the second after a context object or marker (`logger.info({ userId }, "renewed")`, SLF4J markers). It can concatenate literals with expressions (`"Order " + id + " rejected"`) or be wrapped in a format call (`String.format`, `fmt.Sprintf`, `string.Format`, `util.format`). Placeholders such as `${id}`, `{}`, `{UserId}`, `%s`, `%(name)s`, `#{x}`, Kotlin `$name`, and concatenated expressions become wildcards. Messages assembled elsewhere (in a variable or helper) are only attributed by reported location. Indexing covers open editors and up to 5,000 workspace files (`logline.logLensMaxFiles`) of at most 512 KiB, skips common dependency and build folders and calls inside comments, and follows edits and file changes. When an event reports a file the scan did not reach, Logline finds and indexes that file on demand.

Each captured event is attributed to a statement by the code location it reports, when it reports one: the debugger's output location, OpenTelemetry `code.filepath`/`code.lineno` (or `code.file.path`/`code.line.number`), Log4j and Go `source.file`/`source.line`, Python `pathname`/`lineno`, ECS `log.origin.file.*`, or a `caller` such as `pkg/handler.go:42`. Otherwise the message text is matched against the statement's literal text. Short or generic templates (fewer than six distinctive characters) are only matched by location. A message that two statements explain equally well is not attributed to either.

Statements that produced retained events show a CodeLens such as **12 hits · 2 errors · last 3s ago**; click it to filter the Logs panel to those events. When a statement's events report how long something took, in `durationMs`, `duration`, `duration_ms`, or `responseTime` (the fields `durationMs:>200` searches), the lens shows it too: **1,204 hits · p50 12 ms · p95 180 ms**. Percentiles appear once there are at least 5 durations; before that the lens shows the value or the range. They cover the statement's latest 256 retained events that reported a non-negative number, and like the counts, they change as events are evicted. Hover over the statement to see its three most recent messages, how they were matched, and its p50, p95, p99, and maximum duration. With `logline.logLenses` set to `codelens+gutter`, statements that logged errors are also marked in the gutter and overview ruler. Counts cover the retained events and change as events arrive or are evicted; **Clear logs** resets them. Expanded events offer **Open code · file:line** to jump to the statement behind them, and **Logline: Show Log Statements That Have Not Logged** lists statements in the active file without retained events, which helps when a code path was never reached. Set `logline.logLenses` to `off` to stop indexing.

## Log breakpoints

Breakpoints usually stop on code. Log breakpoints stop on what the program logs, which is often how you notice a bug first.

- Expand an event and choose **Break here**. Logline adds a regular debugger breakpoint on the statement that logged the event (found the same way as **Open code**) and opens it in the editor. The next time that statement runs, the debugger stops there, before the line is logged, with the full stack and variables. It is an ordinary breakpoint, so you can add a condition or remove it in the Breakpoints view.
- Choose **More actions → Break on matching logs** to break on the current search and level filter, for example `level:error "payment failed"`. Logline adds breakpoints on up to 10 statements that already logged matching events. It also watches output from debug sessions: when a session logs another matching event that has no Logline breakpoint (for example from a library or a statement it could not map to code), Logline asks the debugger to pause right after it. A notification names the event, with **Show event** and **Remove log breakpoint**. Pausing after the fact cannot stop before the line ran; at most one pause per log breakpoint is requested every 1.5 seconds, and none while the program is already paused.

A status bar item, **Break on log**, shows while log breakpoints are active; click it, or run **Logline: Manage Log Breakpoints**, to see their matches and remove them. **Logline: Break on Matching Logs** asks for a search. Log breakpoints last for the window and work with any debugger that supports the Debug Adapter Protocol `pause` request.

## Log doctor

Log doctor reports problems with log statements in the Problems panel, based on what they actually logged rather than on how the code looks. Findings on statements need log lenses, which match events to the statements they index. Secrets and personal data are also checked in every source's output, including libraries, imported files, terminals, and OpenTelemetry, where no statement is matched: those findings appear in the **Issues** tab and the health report under the source's name, with **Show example** to open the latest event that carried the value with the logs around it. The same findings appear in the Logs panel: the **Issues** tab lists them with **Fix…** (opens the statement with its quick fixes) and **Show events**, rows from a statement with a finding carry a log doctor icon, and expanding such an event explains the finding.

| Finding | Reported when | Severity |
| --- | --- | --- |
| `secret` | A statement logged a JSON Web Token, bearer token, AWS, GitHub, Slack, Google or Stripe key, private key, or a value in a credential field such as `password` or `authorization` | Warning |
| `personal` | A statement logged an email address or a payment card number (grouped like a card, or in a card field, and passing the Luhn check) | Warning |
| `missing-exception` | A statement inside a `catch`/`except` block logged errors without a stack trace and does not pass the caught variable | Warning |
| `noisy` | A statement below warning level produced at least 30% of at least 500 retained events | Information |
| `unstructured` | A statement formats two or more values into plain-text messages instead of logging fields | Hint |
| `quiet-failure` | At least half of a statement's events (and at least 3) are logged at trace, debug, or info but describe a failure: a stack trace, a 5xx status, or a message such as "failed", "refused", or "timed out". Messages that deny a failure, such as "no errors", do not count | Warning |
| `contextless` | Most structured logs carry a trace, request, or correlation id, but at least 3 of a statement's events (most of them) are structured warnings or errors without one | Information |
| `oversized` | A statement's events average 8 KB or more, or some were cut at `maxLineLength` | Information |

Log doctor also checks the OpenTelemetry spans and metrics the receiver keeps against the semantic conventions that matter most when debugging. These findings belong to a service rather than a statement, so they appear in the **Issues** tab under **OpenTelemetry conventions** and in the health report, not in the Problems panel; **Show trace** opens a trace that shows the problem. They are part of `logline.logDoctor` set to `all`.

| Finding | Reported when | Severity |
| --- | --- | --- |
| `unnamed-service` | A service sends telemetry as `unknown_service`, the SDK default when no service name is set | Warning |
| `span-name-ids` | Span names contain ids (numbers of two or more digits, UUIDs, or long hex strings), such as `GET /orders/12345`, so the same operation never groups together | Warning |
| `unmarked-error` | A server span recorded a 5xx `http.response.status_code` but its status is not Error | Warning |
| `missing-route` | At least half of a service's HTTP server spans have a method but no `http.route` | Information |
| `old-attributes` | Spans or metrics use attribute names replaced in the stable conventions, such as `http.method` (now `http.request.method`), `http.status_code`, `net.peer.name`, or `db.statement` | Hint |
| `unit-in-name` | A metric name ends in a unit, such as `checkout.latency_ms`, instead of giving it in the unit field | Hint |

Evidence is always masked: a finding says what was logged and where (`Logged a JSON Web Token in field headers.authorization in 37 events (eyJh…[jwt])`), never the value itself. Examples like `user@example.com` and already redacted values are ignored. Findings follow the retained events, so they update as logs arrive and disappear after **Clear logs**.

Quick fixes (Ctrl+. or Cmd+.) depend on the finding: **Lower to debug** for a noisy `info` or `log` call; **Raise to error** for a failure logged at `info`, `debug`, or `log`; **Pass 'err' to the log call** (or **logger.exception** in Python) for a missing exception; **Fix with Copilot** for secrets, personal data, unstructured messages, exceptions, oversized events, and missing request context, which opens chat with the finding and statement (offered only when GitHub Copilot Chat is installed); **Show the events in Logs**; and **Ignore this finding**, which adds a `logline-ignore: <finding>` comment above the statement. A `logline-ignore` comment without a finding name silences every finding for that statement. **Logline: Show Log Health** opens a Markdown summary of all findings in the workspace, with what to do about each kind, that you can paste into an issue or pull request. Set `logline.logDoctor` to `security` for secrets and personal data only, or `off`.

## Tasks

Logline observes VS Code task lifecycle events automatically. Shell, process, `node-terminal`, and tasks launched through `launch.json` appear in the Logs selector with their task name, dependency information, process id, and exit reason. VS Code does not expose a supported output stream for an arbitrary task, so use **Logline: Convert VS Code Task to Logline** (or **Logline: Capture VS Code Task in Logline**) to create a captured wrapper when the task's stdout/stderr should be retained line by line. The converter follows `dependsOn` links and creates wrappers for supported dependencies too.

New automatic task IDs include the workspace folder, task type, and exact label, so equal labels in different folders and labels with similar punctuation remain separate. Explicit `taskId` values, including IDs in existing converted tasks, are preserved. Dependency status follows the latest matching run in the same folder and recognizes converted task labels. Dependency status indicates whether a task has finished, not whether it succeeded.

Servers can also be started as a VS Code task, with output streamed into the same Logs panel. Tasks are discovered in every workspace folder and run in their own folder's scope. Conversion preserves existing task comments and rejects malformed task files or files changed on disk while its picker was open. Add a task of type `logline` to `.vscode/tasks.json` — comments and trailing commas are fine, it's read as JSONC:

```jsonc
{
  "version": "2.0.0",
  "tasks": [
    {
      "type": "logline",
      "label": "Run API",
      "command": "npm",
      "args": ["run", "dev"],
      "jsonOnly": false,
      // "shell": false,
      // "dependsOn": ["Logline: Build"],
      // "dependsOrder": "sequence",
      // "options": { "cwd": "${workspaceFolder}/server", "env": {} }
    }
  ]
}
```

Supplying `args` selects literal argument mode by default, including `args: []`. Arguments containing spaces or quotes are passed directly to the process unless `shell: true` is set.

Set `shell: true` when the command is a shell line containing pipes, redirects, or shell operators. Task variables such as `${env:NAME}`, `${config:logline.source}`, and `${input:name}` are resolved by VS Code immediately before the Logline task starts, including variables in `command`, `args`, `options.cwd`, and `options.env`. `jsonOnly: true` applies to this task only and drops non-JSON lines while retaining structured output.

## Status and troubleshooting

Run **Logline: Show Status**, click the check mark at the right of the status bar, or choose **Status and troubleshooting…** in the Share panel, to see what Logline is doing in this window, with a fix for anything off or broken:

- **OpenTelemetry receiver**: its address and how many traces and metric series it holds. If the port was in use and the receiver took another one, apps configured for the usual port are sending elsewhere; the item opens `logline.otlp.port`.
- **Claude Code and Codex**: whether MCP clients can reach this window, which agents called recently, and which have the Logline skills.
- **Sharing with agents**, **Terminal capture**, and **Debug sessions**, with the command that turns each on or off.
- **GitHub Copilot**, when it is not installed: Ask Copilot and Fix with Copilot need it; everything else works without it.
- **Retention**: events and memory used, and whether old events are being dropped.
- **Log lenses and log doctor**, and **My changes**.

Choose an item to run its fix, or **Copy status** for a bug report.

## Editors other than VS Code

Logline also runs in editors built on VS Code 1.99 or later, such as Cursor, Windsurf, and Kiro. Download `logline-<version>.vsix` from the [latest release](https://github.com/SurjeetBanga/logline/releases/latest) and run **Extensions: Install from VSIX…** in the editor. ## Bounded retention

Numeric settings are clamped to their documented ranges; event counts, line lengths, indentation, and refresh intervals use whole numbers. Invalid setting types fall back to defaults. Malformed saved servers are ignored for execution, `autoStart` requires the boolean `true`, and only string environment values are passed through. Preferred columns are limited to 200. Manage servers distinguishes duplicate labels by ID.

The viewer retains up to **50,000 events or 100 MiB** of estimated event storage by default, whichever limit is reached first. The estimate includes top-level strings, flattened field names and values, dependency strings, and approximate object/property overhead. It is not a bound on total VS Code memory: indexes, temporary exports, and browser DOM storage add overhead. Older events are evicted automatically, and the footer shows the live figure against the configured budget. Raising or lowering `maxEvents` or `maxMemoryMb` takes effect immediately, without reloading the window. Wide structured logs may reach the memory limit before the event limit.

Search and analysis cover retained history only; enable `persistLogs` or use a log service for archival storage. Persisted logs are written to `.logline/` in the first workspace folder — add that directory to your `.gitignore`.

Disk persistence buffers up to 8 MiB of estimated text storage, including writes in progress. If the disk falls behind, new disk writes are skipped until space becomes available; live capture continues. Write failures also warn and count the affected batch's lines in the footer's **disk writes skipped** counter; later batches can continue. Accepted writes remain ordered. Each rollover retains one previous file, so disk use can approach twice `maxDiskMb`, plus a batch. Field-name indexes release names when their last retained event is evicted, and each event exposes at most 120 flattened fields, including MDC fields; the original raw event remains available within the line-length limit.

Redaction applies to exports and **Copy filtered results** when enabled; shared-agent results are always redacted. **Copy** on an expanded event and disk persistence retain original content. Additional `redactionFields` match structured field names; free-text redaction recognizes common credential assignments. If valid JSON is too deeply nested to redact and serialize, its exported raw payload is replaced entirely with the redaction marker.

## Workspace trust

The extension runs server commands defined in workspace settings and tasks, and opens the databases in `logline.connections`, so it is disabled in restricted mode and in virtual workspaces. Trust the workspace to use it.
